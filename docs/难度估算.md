# 难度估算

进关卡后，Mod 只看这一关自己要按的砖，估一个 TUF（The Universal Forums）风格的难度档位（P1–P20、G1–G20、U1–U20），画在 BPM 框左半边。官方曲目和创意工坊谱面都一样估。设置窗口「外观」页的「估算难度」可以关掉。

这是**估算**，不是 TUF 的官方评级：徽章下面写着「估算」，设置里的说明也这么写。

这是**试验性功能**（2026-11-19 定）：设置里的开关旁标着「试验性」。现在的精度见下面的「校准数据和误差」，P 档大多差 1–2 档以内，G、U 档常差 3–4 档；要很多键的 U 档谱容易估低，按规则评级（限键、判定限制）的谱估不准。

## 怎么估

1. 游戏里读到这一关要按的砖（和排键用的同一份 `TileHit`），按关卡设定的音高（`pitch`）换算成实际播放的秒数。练习时临时调的速度不算：TUF 按原速评级。
2. `DifficultyEstimator.Measure` 算 15 个特征：

   | 特征 | 意思 |
   |---|---|
   | logHits | 一共按几下（取对数） |
   | logSeconds | 从第一下到最后一下多少秒（取对数） |
   | meanNps | 平均每秒几下 |
   | dens50 / densMax | 每个音符前后 1 秒内每秒按几下，取中位数、最大值 |
   | fast60 | 间隔短于 60 毫秒的比例 |
   | chord | 间隔短于 25 毫秒（同时按：多押、伪双押）的比例 |
   | strain0.3 / strain4.0 | 负荷：每按一下加 1、按半衰期 0.3 秒 / 4 秒衰减，从大到小加权平均；短的看爆发，长的看耐力 |
   | gapEntropy | 间隔种类有多杂（节奏越杂越高） |
   | fastTrigram | 快的地方的节奏花样：每三个相邻间隔看成一个花样（间隔按 1/4 个八度分组），只算第一个间隔短于 150 毫秒的，取花样的熵。整齐的连打是 0 |
   | peakVariety | 最难几段的节奏种类：每隔 1 秒取一个 4 秒窗口，间隔种类数 × 每秒几下，取 95% 分位。又密又杂才高 |
   | speedJumps | 每分钟突然变速几次：「每度转角用多久」（星球转得多快）和上一下比变了 1.4 倍以上 |
   | rollShare | 滚键组：相邻间隔都短于 70 毫秒的一串要在一只手上滚过去，一组几个音要几个键。在 5 个音以上的组里的音符占几成 |
   | rollSize | 滚键组有几个音，取 95% 分位（取对数） |

3. `DifficultyModel.g.cs`（梯度提升树：很多棵小判断树的结果加起来）把特征换成 1–60 的分数，四舍五入成档位。

## 校准数据和误差

- 数据：用 TUF 的公开接口按档位抽样，每档按通关数从多到少取 15 张已评级的谱面，只下 `.adofai`（不含音频），一共 825 张、约 400 MB（P1–U14 各 15 张，U15 只有 12 张、U16 只有 3 张；U17–U20 在 TUF 上还没有评过的谱）。谱面和评级不进仓库，放在仓库外的文件夹。
- 能用的 748 张：77 张用了离线读谱没模拟的事件（多星球等）或 angleData 里夹着 null，时间可能不准，不参与拟合。
- 10 折交叉验证（拿 9 份拟合、猜剩下 1 份，轮一遍，换三种划分取平均）：

  | | 平均差 | 差 ≤1 档 | ≤2 档 | ≤3 档 | ≤5 档 | ≤8 档 |
  |---|---|---|---|---|---|---|
  | 全部 748 张 | 2.77 档 | 32% | 56% | 69% | 85% | 95% |

  分大档：P 平均差 1.66，G 3.67，U 3.13。整体不偏，整体加减几档只会更差（第二轮时试过：加 1 档 3.35 → 3.55）。
- 还剩的偏差：P16–G5 一带平均估高，U 档平均估低约 2 档。同一个真实档位估出来散得开，所以按估出来的档位分段加减也没用（试过）。
- 按 TUF 参考谱的类型看（见第三轮）：要很多键（KEYCOUNT）的 U 档谱仍估低约 2.5 档，同时按（PSEUDO）的谱估高约 1.5 档。
- 第一批每档只有通关最多的 5 张时，交叉验证是 3.33 档；那批谱更典型，结果偏乐观。

### 第二轮：节奏有多杂（2026-11-19）

只看密度的第一版（14 个特征里有 share15、longStream、speedChanges，没有后三个新特征）交叉验证 3.43 档，G 档 4.52。把它估错最多的谱列出来：

- 估高的几乎都是整齐的长连打：Speed Test、Heaven's Gateway 的几个简化版、Electric Butterfly (No Key Limit)、RUSH E、600 BPM 的 COFFEE RUN；
- 估低的是节奏花、变速多的谱：Adcar、PIONEER、Janus、Crimson Night、Turkey Turkey。

也就是说密度一样时，节奏越乱越难，第一版没看这一点。按这个方向试了四组候选特征（交叉验证平均差，越小越好）：

| | 平均差 | P | G | U |
|---|---|---|---|---|
| 第一版 14 个 | 3.43 | 2.01 | 4.52 | 3.97 |
| + 节奏复杂度 12 个 | 2.92 | 1.84 | 3.84 | 3.18 |
| + 转角 5 个（快的地方转角是否一致、急转弯等） | 3.28 | 1.95 | 4.26 | 3.85 |
| + 变速幅度 2 个 | 3.40 | 2.04 | 4.49 | 3.85 |
| + 关卡事件（镜头、轨道动画、滤镜等每分钟几次） | 3.48 | 2.14 | 4.53 | 3.95 |

再逐个加、逐个删，留下 fastTrigram、peakVariety、speedJumps 三个，换掉作用最小的 share15、longStream、speedChanges，特征总数不变，得到 2.87 档（P 1.80 / G 3.74 / U 3.19）。

- 关卡事件没用，正好：游戏里官方关卡读不到事件，用了反而估不了官方曲目。
- 「快的地方的节奏能压缩多少」（zlib 压缩率）单独看也有用（再降约 0.05 档），但不同运行环境的 zlib 压出来大小不一样，游戏里和校准时算的会对不上，没用。
- 换更大的树（深 4、200 棵）只到 2.84，在误差范围内，模型大 4 倍，没换。
- 带「No Key Limit」「4K Limit」「Judgement Limit」这类后缀的谱，是按谱面以外的规则评级的（限不限键、判定限制），只看砖块估不准。「Nerfed」「Remake」是另一张谱，砖块本身变了，不受影响。

### 第三轮：照社区的评级方式（2026-11-19）

TUF 评级主要靠和每档的参考谱比（2026-11 起每档 8 张，公开接口 `GET api.tuforums.com/v2/database/references`，60 档共 396 张，U13 以上还没有）。每张参考谱标了难在哪一类，可以组合：

| 类型 | 意思 |
|---|---|
| ROLLING | 滚键：快到要几个键轮着滚过去 |
| KEYCOUNT | 一口气要滚的音太多，要很多键 |
| TECH | 节奏花、变速、要反应 |
| PSEUDO | 同时按（伪双押、多押），只在 P 档 |
| INDEXING | 社区没有公开定义，看参考谱像是比滚键慢一档、两手交替一下一下点 |

校准集里正好有 231 张参考谱。第二轮的模型按类型看：KEYCOUNT 平均估低 1.4 档（U 档 2.7 档），TECH 的 U 档估低 2.5 档，PSEUDO 估高 1.8 档。照这五类设计候选特征（滚键组的分法参考了滚键练习工具：间隔够短的一串在一只手上滚完，一组几个音要几个键）：

| 加上 | 平均差 |
|---|---|
| 第二轮 14 个 | 2.87 |
| + 滚键组（ROLLING / KEYCOUNT）7 个 | 2.88 |
| + 交替段落（INDEXING）3 个 | 2.89 |
| + 同时按（PSEUDO）7 个，含按「动作」算的密度 | 2.85 |
| + 4 倍以上的突然变速、几连音 | 2.87 |
| + 长按、时长、休息占比、Twirl 次数 | 2.82 |

一组一起加反而被别的特征稀释，逐个加、贪心选出来的是时长（logSeconds）和两个滚键组特征。滚键组按 70 毫秒分比按 86 毫秒准。「每分钟几个大滚键组」在整首一直滚的谱上只算 1 组，换成 rollShare（在大组里的音符占几成），误差一样、没有这个问题。再去掉作用最小的 gap25、dens90，得到 15 个特征、2.77 档。

- 没用的：同时按、交替段落、几连音、长按、Twirl、训练时去掉按规则评级的 11 张谱、换成 Huber 或绝对误差拟合
- 深 4 层、150 棵树能到 2.70，模型大一倍多，没换
- 滚键组特征之后，KEYCOUNT 的 U 档仍估低约 2.5 档：U 档校准谱少（180 张，U16 只有 3 张），树模型又不外推
- TUF 自己在做评级机器人 AutoRater（闭源，4 个模型取平均，平均算一张管理员票）；TUFRater（GitHub 上的另一个尝试）只用砖数、BPM、Twirl 和变速次数等很粗的特征
- 只看按键时间和转角，不看画面特效、隐藏砖这类读谱难度；也不看判定限制、限键这类 TUF 会另外考虑的东西。
- 树模型不会外推：比校准数据里最难的谱（U16）还难的，也只会估到那附近。

## 重新校准

需要 .NET 10 SDK，以及 Python 的 numpy、scikit-learn（只在开发时用，Mod 不需要）。

1. 准备文件夹（仓库外）：`index.json`（`{"<编号>": {"tier": "G12", ...}}`）和 `levels/<编号>.adofai`。
2. 用 Core 算特征（和游戏里同一份代码）：

   ```powershell
   dotnet run tools/Difficulty.cs -- export <文件夹> features.csv
   ```

3. 拟合并生成模型（会打印交叉验证误差，覆盖 `src/RhythmHint.Core/DifficultyModel.g.cs`）：

   ```powershell
   python tools/difficulty-fit.py features.csv
   ```

4. 核对 C# 和 Python 一致：下面打印的平均差应该和上一步「全部数据拟合」的一样（这是训练集误差，偏乐观，真实误差看交叉验证）。

   ```powershell
   dotnet run tools/Difficulty.cs -- evaluate <文件夹>
   ```

改了特征（`DifficultyFeatures.Names` 或 `Measure`）就要重新跑 2、3 步；`difficulty-fit.py` 按名字核对，CSV 里缺特征会直接报错。

估一张谱看看特征：

```powershell
dotnet run tools/Difficulty.cs -- level <关卡.adofai>
```

离线读谱是宽松版（`src/RhythmHint.Reference/AdofaiLevelReader.cs`）：算 SetSpeed、Twirl、Pause（含游戏对 9–16 版暂停的迁移）、Hold、AutoPlayTiles 和中旋，能修三种老谱 JSON 写法（对象属性之间两个逗号、数组属性后漏逗号、数组里两个对象之间漏逗号）；多星球、自由区、带 angleOffset 的变速、angleData 里的 null 记为「时间可能不准」。游戏里用的是游戏自己算的砖块时间，不经过它。
